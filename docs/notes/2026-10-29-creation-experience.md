# 创建体验记录：湖边钟表匠

日期：2026-10-29。通过 Orca 浏览器操作本机原型，用已配置的真实模型和独立的临时存档体验；没有修改作者原有的《红发会》草稿。这里记录一次体验，不代表所有模型和场景的成功率。

## 体验经过

目标是从一句想法创建湖边木屋：可以进入，有窗户、工作台和桌椅，住着一位修钟表的老人，观察他修理怀表的一天。

1. 第一轮助手提出湖岸、木屋、老人和小船，并询问开始时间及希望看到的变化；没有实际建造。
2. 我指定上午开始、怀表在晚上前修好，并明确要求建造。助手说先搭湖岸和木屋，但画布仍空、撤销不可用；第二轮至少等待约 59 秒。截图保存在本机临时路径 `.tmp/prototype/experience-review/screen.png`，不作为永久或可共享的验收产物。
3. 再次要求实际建造后，界面显示“建造未完成：方块类型未注册”。
4. 我要求仅用已有的木头、石头、玻璃、水和草，界面显示“建造未完成：区域起点必须小于或等于终点”。
5. 我把要求缩小为一块草地并提示坐标顺序，界面显示“模型没有返回可用的讨论回复”，附有 `reply`、`summary`、`ready` 等格式信息。

五次输入后没有可见建造结果，也没有出现查看起点草稿的入口，因此没有体验确认进入、人物行动或成品场景。截图只能证明当时画布为空，不能由此判断渲染器在有内容时的表现。等待时间是一次观察，并非性能统计；模型输出和调用审计留在本机临时存档，不纳入仓库。

## 发现的问题

1. **表达与事实脱节。** 助手描述接下来要搭建的东西，但页面缺少明确的“仅为计划／已提交／失败”区分；这次画面和撤销状态没有显示任何已提交的建造。
2. **失败恢复依赖用户懂内部细节。** 材料名、坐标和响应格式直接暴露给用户，错误没有指出如何恢复；连续失败后，用户原本想要的世界仍然不存在。
3. **进展反馈不足。** 至少一次等待接近一分钟，用户只能等待而看不到实际建造进展。当前信息不足以判断延迟由模型、网络还是其他环节造成。
4. **对话没有带来可见成果。** 多轮讨论、反复确认和重新描述之后，仍没有第一片可检查的场景。用户提出的“先开始建”没有可靠变成执行。
5. **失败破坏对话连续性。** 检查 `world-creation.mjs` 可见：用户消息先保存，命令校验失败时助手回复不写入对话，错误通过独立状态显示。体验中因此连续出现用户消息，失败原因也需要用户自己转述。

补充代码观察：`creation-dialogue.mjs` 允许 `commands` 为空，`world-creation.mjs` 会在通过回复格式检查后使用模型的 `reply`；是否出现建造描述与实际修改不一致，取决于模型输出，不能仅靠提示词保证。`voxel-building.mjs` 和 `voxel-tools.mjs` 拒绝未知材料与倒序坐标，但当前错误没有包含用户可操作的恢复路径。这些是对实现的分析，不是对模型内部原因的证明。

最终这一份起点经历 8 次模型调用，生成工作累计 58.2 秒；此前另有一份失败起点用过 6 次调用，不能把前者当成全部成本。确认后首次人物行动成功仅证明一次行动，未验证完整一天或长期表现。起点预览及进入世界后的本机截图因页面处于隐藏状态、未绘制帧而超时；已用网页可访问性树和保存状态核对进入及行动，没有据此声称看过最终运行画面。

根据复验继续补了两项工具能力：精确部件归属与换色，以及单层矩形空间检查。程序对这份真实旧场景发现 22 处墙顶开口，窗户的旧记录也没有精确归属，与多角度查看时的质量问题一致。新能力已通过定向和最新云端浏览器回归；云端还确认石色屋顶只改变归属方块，旁边未归属木块保留。加入后的本机可用内存持续低于 4 GiB GUI 门槛，暂未启动新一轮本机 GUI 演练，不能声称新模型建造质量已经改善。

## 再次打开原型后的画面验收

2026-10-29 再次打开隔离的 5186 原型服务，用无头 Chrome 实际读取页面并保存临时截图。页面左侧不是持续空白：在场景完成初始化后，体素 canvas 有 839×780 的可见绘制区域，能看到草地、湖水、木屋、屋顶和人物；右侧动态能显示已发生的修表行动。此前看到的整块空白来自异步渲染尚未完成时截取页面，产品状态没有解释这段等待。

这次还发现世界被真实模型的一次无效决定卡在 `actor:invalid-decision`。画面原先把主按钮保留为“暂停”，但下一步行动按钮被禁用，用户很难判断如何继续。现在载入期间显示“正在载入画面…”或“正在载入体素画面…”，成功后会移除载入节点；无效决定时主按钮显示“等待中”并禁用，操作区显示“解除等待”，时钟提示“等待处理 · 解除等待后可以继续”。载入失败会保留文字动态，并显示具体载入原因和重新载入按钮。

这次修改后的定向 UI 回归为 28/28，页面无控制台错误。当前隔离服务仍使用真实模型验收存档；无效决定状态只记录在该临时存档中，没有修改作者原有存档。

### 复盘后落地的体验改进

随后用 ZCode Desktop 在同一项目目录 `/home/neo/Projects/Wispiva-prototype` 做了一次只读交叉审查。它确认最影响体验的是首片场景成功周期过长、等待像卡死、场景问题需要用户自己翻译成修复请求；这与本次真实记录相符。基于这次审查，原型又落地了三项小改动：

1. 等待面板显示阶段、模型请求次数和已接收字数，起点生成显示 `阶段 n/3`。
2. 空间检查面板自动展开，并提供“让助手处理”入口，把检查结果组成下一轮建造请求。
3. 创建对话限制每轮最多 24 条命令，并要求一次只做一个部件，减少长命令链的整批失败。

在 2026-10-29 当时，本地 `npm run check` 通过了 135 个 Node 测试、282/282 项环境检查和 40/40 条模型客户端观察；没有读取私有模型配置，也没有发起真实模型请求。这是当时的验证记录，当前工作树的最新检查数字见[工作计划](../PLAN.md)。以上改动改善反馈与恢复路径，但没有证明真实模型已经能稳定做出合格木屋；空间质量仍需下一轮隔离真实体验复验。

### 真实模型复验：短步骤与空间修复

在 2026-10-29 晚间使用新的隔离存档重新调用真实模型，存档位于本机临时目录 `.tmp/prototype/live-recheck-20261029`，没有触碰 5186 服务存档或《红发会》存档。

| 步骤 | 结果 |
| --- | --- |
| 首次只建地板 | 模型第一次漏掉对象登记，27.1 秒后原子失败；补充明确的对象格式后，45.8 秒提交 9 格地板和 1 个 building 对象。 |
| 墙体和门洞 | 20.0 秒提交 62 格墙体，门洞本身被清出，但门洞外没有地面，检查仍提示入口问题。 |
| 窗户 | 15.6 秒登记了 window 对象但选中了已清空的门洞，没有替换方块；检查保留“窗户无精确归属”。 |
| 屋顶 | 13.9 秒提交 25 格坡顶，保留室内空气。 |
| 一键处理检查项 | 先有一次 12.9 秒无变化；加入“门外需要 grass、窗户不能选门洞”的诊断后，另一次等待 174 秒仍无正文，随后中断并安全恢复。 |
| 两个明确微修复 | 10.5 秒补上门外 1 格 grass；9.3 秒把仍有木墙的位置替换为 2 格 glass，并建立精确窗户归属。 |

最终场景为 97 格、3 个对象，门洞、屋顶覆盖、窗户嵌墙与水相交检查全部通过。这个结果证明短步骤和精确部件归属能在真实模型下完成可验证修复，也证明“一键处理全部检查项”太宽，因此已改成一次只修一个检查问题。有限空间检查通过不等于湖岸、家具和多角度视觉质量合格。

改成单问题入口后，内存 UI 回归确认按钮只发送第一项诊断，并携带对象 ID、问题代码和修复建议。用缺少门外 grass 的隔离场景做真实复验时，第一次请求 57 秒后返回截断，产品重试再次以网络错误结束；两个请求都没有修改场景，当前版本保留了原意图和版本。随后补充了更具体的边界提示：门洞清空操作带 `objectId`，建筑外的 grass 操作必须省略 `objectId`，不能把门外地面登记为建筑成员。

在新的隔离副本 `.tmp/prototype/live-repair-hint-2-20261029` 中重新请求同一项修复，模型最终按两个操作完成：清出两格门洞，再补一格门外 grass。场景从 96 格、版本 6 变为 95 格、版本 7，`cabin-main`、`cabin-window` 和 `cabin-roof` 均保留，空间检查为 0 项。这个请求耗时 144.3 秒，首段正文在约 140.3 秒才到达；因此修复边界更清楚了，但等待体验仍然不合格，不能把一次成功当成稳定性证明。

随后把这两类边界明确的修复做成画布上的“直接修复这一项”：入口问题直接清出门洞并补门外 grass，窗户问题直接登记精确范围并把仍为 wood 的墙格替换为 glass。直接修复走本地原子事务，不调用模型，失败会保持原场景；其余问题仍保留“让助手修复”入口。这样用户可以先完成安全的局部修复，再把模型留给需要判断的空间问题。

同时调整了体素画布的展示：小场景取景距离收紧约四分之一，并加入 512 分辨率的软阴影，让屋顶、墙体、人物和地面之间形成接触层次。这个改动已通过语法、UI 和完整离线回归，真实浏览器画面仍需下一次可用的 GUI 验收确认。

### 等待与模型边界

当前配置及同服务模型列表只提供 `spark-x2.6`，无法完成多个模型的对比。以下仅是同一服务的参数试验，没有修改用户的 `.env`；提示、场景与操作曾变化，不能据此宣称稳定加速。

| 条件 | 一次或多次实测 |
| --- | --- |
| 原提示、供应商默认 | 36.4 秒提交，但成品质量不合格；首段正文约 23.2 秒。 |
| 精简建造提示、供应商默认 | 两次等待 218.3 秒、367.2 秒后手动取消；连接约 1.6／2.6 秒，均未观察到正文。 |
| 可选 low／medium | 分别约 24.8／13.5 秒结束，均没有可用正文；没有把推理内容冒充最终输出。 |
| none | 多次得到正文，但仍有材料、JSON 格式和空间错误；建造约 24.0 秒、修建约 29.7 秒，拆开的屋顶／窗修改约 9.1／9.6 秒，另有 60.8 秒的格式失败。 |

2026-10-30 复核了调用审计：上表记录的模型 ID 都是 `spark-x2.6`；变化的是 `reasoning_effort`，并非三次模型切换。low 和 medium 的复杂任务请求都收到 HTTP 200、状态 `completed`，但没有最终文本；调用分别产生 903 和 414 个 reasoning tokens，原型因此按 `empty-content` 拒绝。none 与默认设置的历史请求能返回正文，但建造结果仍有质量和格式问题。用同一模型和短 JSON 请求隔离复测时，默认、low、medium、none 均在约 2.6–3.3 秒返回可见正文。故接口、凭据及这些设置本身可用；空正文只在旧的复杂任务样本中复现，具体由哪段提示或请求内容触发尚未确定。讯飞当前 [Responses 文档](https://maas.xfyun.cn/doc/guide/3%E3%80%81API%20%E6%8E%A5%E5%8F%A3/3.1%20%E6%98%9F%E7%81%AB%E6%A8%A1%E5%9E%8B%20API/3.1.2%20Responses.html)列出 `spark-x2.6`、Responses 接口及这些 reasoning effort 取值。

原型没有运行时模型选择器；服务在每次请求时读取配置，进程环境变量优先于 `.env`，也可由 `WISPIVA_ENV_FILE` 指定配置文件。当前 `.env` 仍指向 `spark-x2.6`。若曾把 `.env` 改成其他模型而审计仍显示该 ID，应核对服务启动时的 `WISPIVA_LLM_MODEL`／`WISPIVA_ENV_FILE` 覆盖；旧服务进程已退出，无法从本机还原其启动环境。日志也没有包含所说另外三个模型 ID，因此不能据此断定那些模型具体失败原因。

局部修改原先逐格发送场景。756 格样本合并为 146 个同材料区间，场景上下文由 31,683 字符降到 8,047 字符，减少约 75%；回归逐格展开验证内容一致。这是输入体积测量，不证明响应时间按同一比例下降。

本地样本：Ubuntu、视口 1256×990、DPR 1.333；一次导航的 DOMContentLoaded 44.1 ms、load 51.9 ms。1.5 秒静态页的 requestAnimationFrame 回调间隔中位数约 6.1 ms，**不是实际 GPU 渲染帧率**；渲染器按需绘制。隔离 Node 服务一次 RSS 约 90 MiB，浏览器共享进程无法单独归因。尚无大场景或长期运行性能结论。

### 我的体验判断

修复后能看见实际变化、知道失败是否改了场景，也能从失败继续。这些改善消除了“说建好了却不知道发生了什么”的一部分困惑。

但创建仍需要多次纠错和拆分请求。方块数增加并不等于空间成立；当前木屋像粗糙的搭块，门窗、墙体与家具缺少清晰关系。室内查看帮助暴露问题，没有解决模型的空间规划。

因此，本轮不能以回归全绿或主流程走通称为体验合格。反馈与恢复的改善明确，空间质量仍然差。精确部件工具和空间检查已补上，接下来要验证真实模型是否能准确使用它们，再评价视觉表现和持续角色行为。当前验收状态与后续工作统一维护在[工作计划](../PLAN.md)。
